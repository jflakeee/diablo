# 모바일 스킬 버튼 이모탈식 부채꼴 배치 (1단계)

작성일: 2026-10-04
대상: `prototype/game_dungeon`
상태: 구현 기준 확정

## 1. 배경과 범위 결정

`prompt_diablo.md` 21번 "UI는 디아블로 이모탈 모바일 버전으로 최적화"는 범위가 넓어
한 사이클로 끝낼 수 없다(인벤토리 그리드 UI 라운드에서 D2식 드래그앤드롭 격자를 같은
이유로 비범위 처리한 전례와 동일 — `docs/PROJECT_MEMORY.md` 141~143행). 전체를
이모탈과 1:1 대조하는 감사는 별도로 필요하고, 이번 라운드는 **가장 눈에 띄는 단일
시각 요소 하나**만 이모탈식으로 바꾼다.

이모탈 모바일 HUD의 가장 식별력 있는 특징은 스킬 버튼이 사각 그리드가 아니라
엄지손가락 피벗(화면 우하단 모서리) 주위로 **부채꼴(호)을 그리며 배치**된다는 점이다.
현재 `mobile_ui.gd layout()`은 4개 스킬 버튼(`skill_primary/secondary/utility/
quaternary`)을 2x2 사각 그리드로 배치한다(`skill_button.gd`가 이미 원형으로 그려서
버튼 자체 모양은 이모탈과 유사 — 배치 방식만 다름). 이번 라운드는 **이 4개 버튼의
좌표 계산만** 부채꼴로 바꾼다. 버튼 크기, 아이콘, 쿨다운 시각 효과, 입력 처리,
조이스틱/포션/미니맵/메뉴 위치는 전부 비범위.

별도 브레인스토밍이 필요한 나머지 이모탈 대조 항목(기본 공격 버튼 분리, 궁극기
버튼 차등화, 좌측 조이스틱+우측 스킬 휠 전체 재배치 등)은 다음 라운드 후보로 남긴다.

## 2. 접근 방식

- **A안(채택, 2단 구조로 수정)**: 우하단 모서리는 기존 `skill_primary` 그리드
  위치를 그대로 유지(엄지 안착점)하고, 나머지 3개 버튼만 같은 피벗 중심
  180°(왼쪽)~270°(위쪽) 90° 호에 반지름 R=skill_size.x*1.5로 부채꼴 배치.
  처음에는 4개 전부를 호에 균등 배치하는 안을 시도했으나 `validate()`(AABB
  경계 박스 겹침 검사)에서 중간 두 버튼(45° 간격)이 겹치는 것으로 FAIL —
  정사각 버튼은 대각 방향 간격이 축 방향 간격보다 좁아(45°에서 체감 간격이
  cos45°배로 줄어듦) 겹침을 피하려면 R을 2.7배 이상 키워야 했는데, 그러면
  세로 최소 뷰포트(가로모드 640x360 기준 가용 높이 328px)에서 호가 화면
  밖으로 나가 해가 없는 제약이 됐다. primary 고정 + 3버튼 호 구조는 이모탈의
  실제 계층(모서리 큰 버튼 + 주위 호를 그리는 스킬들)에도 더 가깝고, R=1.5배로도
  모든 쌍이 안전 여백을 두고 비겹침(대각 쌍 118.8px 갭 vs 112px 버튼, 최소
  여유 6.8px) — `mobile_ui.gd layout()` 내부 좌표 계산만 교체, 다른 함수/구조
  변경 없음. 기존 `validate()`가 필요한 불변식을 이미 검사하므로 새 테스트 없이
  기존 `selftest()`를 정답 오라클로 파라미터를 튜닝했다.
- B안(기각): 2x2 그리드를 유지하되 45° 회전한 다이아몬드 배치 — 이모탈과의
  시각적 유사도가 낮아 "가장 눈에 띄는 변화"라는 목표에 못 미침.
  C안(기각): 홀드 시 펼쳐지는 라디얼 메뉴로 완전히 새로운 상호작용 추가 —
  입력 처리 재설계가 필요한 다단계 작업이라 1사이클 범위 초과.

## 3. 완료 조건

1. `MobileUI.layout()`이 모바일 프로필에서 `skill_primary`는 기존 모서리 위치를
   유지하고 나머지 3개 스킬 버튼을 같은 피벗 중심 부채꼴 좌표로 반환한다
   (데스크톱은 기존 좌측 확장 가로줄 유지, 마우스 중심 UI라 부채꼴의 이점이 없음).
2. 기존 `MobileUI.validate()`가 검사하는 두 불변식을 모든 기존 테스트 뷰포트
   (960x540, 960x720, 1280x720, 1600x720 × mobile/desktop)에서 그대로 통과한다:
   안전 여백 내부, 스킬 버튼 4개 + 포션 2개 + 미니맵 + 조이스틱 간 쌍쌍 비겹침.
3. 세로/가로 모바일 두 경우 모두 부채꼴이 화면 안쪽을 향한다(바깥으로 잘리지
   않음) — 구현 결과 피벗(우하단 모서리 - 버튼 절반 크기)과 반지름이 두 방향
   모두에서 안전해 분기별 조정 없이 단일 피벗으로 충분했다(`portrait_mobile`
   분기 자체는 메뉴/미니맵 쪽 기존 로직이라 그대로 유지).
4. `prototype\game_dungeon\tools\samples`류 기존 애셋/다른 UI 요소 비변경.

## 4. 비범위

- 스킬 버튼 크기·아이콘·쿨다운 렌더링(`skill_button.gd`) 변경 없음.
- 기본 공격 버튼 분리, 궁극기 버튼 차등화(이모탈은 5~6개 버튼 계층 구조이지만
  이 프로젝트는 4개 동등 액티브 스킬 구조 — 게임플레이 변경 없이 기존 4버튼만
  재배치).
- 조이스틱/포션/미니맵/메뉴(Char·Shop·Bag) 위치 변경 없음.
- 데스크톱 프로필 레이아웃 변경 없음(마우스 입력이라 부채꼴 동기 자체가 없음).

## 5. 검증

- `godot --headless --path . -- autoquit barb`/`sorc`에서 `[ACCESS]`
  (반응형 UI 셀프테스트를 포함하는 기존 집계 체인) PASS 확인 — `MobileUI.selftest()`
  가 이미 해당 체인에 묶여 있는지 먼저 확인하고, 안 묶여 있다면 세션 교훈
  (craft_selftest 미집계 사례)에 따라 편입한다.
- `tools/progression_combat_test.gd` 재실행.
- playwright로 모바일 뷰포트(세로 390x844, 가로 844x390) 접속 후 스크린샷 —
  4개 스킬 버튼이 우하단 모서리를 감싸는 부채꼴로 보이는지 육안 확인(이번
  세션에 새로 도입한 배포 후 시각 검증 단계와 동일 방식, 배포 전 로컬 export
  미리보기로 선행 수행 가능하면 그쪽을 우선).

## 6. 중요 발견과 범위 재조정 (시각 검증 중 발견)

실제 배포 URL을 모바일 UA로 접속해 스크린샷을 찍어보니 **스킬 버튼이 화면에 전혀
보이지 않았다**. 원인을 추적한 결과 `mobile_ui.gd layout()`이 계산하는 4개 좌표
(`skill_primary/secondary/utility/quaternary`)를 실제로 읽어 버튼을 생성하는 코드가
`main.gd`의 `_ready()`에 없었다 — `_add_skill_button()` 함수 자체는 존재하지만 호출부가
없는 죽은 함수였다.

`git log -S"_add_skill_button(ui"`로 추적한 결과, 이 호출부는 버그로 사라진 게 아니라
**2026-09-29 사용자 직접 커밋 `aaac80b "Remove skill controls and pause on modal UI"`**
에서 의도적으로 제거된 것이었다. 같은 커밋이 동시에 처리한 것: 숫자키(1~4) 스킬
단축키 제거, WASD 이동 제거(화살표만 유지), `_auto_play()`를 모든 클래스가 기본
공격만 쓰도록 단순화(소서리스 주문 순환/블링크 카이팅, 바바리안 Iron Chant 자동시전
제거), 모달 패널이 열려 있으면 `_physics_process`/`_process`를 건너뛰는 일시정지 추가.
즉 "수동 스킬 조작을 없애고 기본 공격 자동전투 + 모달 일시정지로 단순화"하는
일관된 설계 변경이었다.

사용자에게 확인한 결과: **9/29 결정을 유지, 스킬 버튼은 다시 연결하지 않는다.**
따라서 이번 라운드의 완료 조건을 다음과 같이 재정의한다 — `mobile_ui.gd layout()`의
부채꼴 좌표 계산은 그대로 두되(향후 수동 조작을 다시 도입할 때 바로 쓸 수 있는 준비된
죽은 코드로 유지, 기존 2x2 그리드도 어차피 똑같이 미소비 상태였으므로 "더 나빠진 것"은
없음), `main.gd`에 버튼 생성 호출부는 추가하지 않는다. 실제로 당장 화면에 보이는 변화는
없다 — 이 라운드의 실질적 산출물은 "좌표 계산 로직 자체의 겹침 버그 수정"과 "이 좌표가
어디에서도 소비되지 않는다는 사실의 문서화"다.
